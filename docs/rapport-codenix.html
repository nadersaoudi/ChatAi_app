1. Présentation générale

Codenix est une application web full-stack : frontend Next.js, backend FastAPI. Un utilisateur authentifié (Clerk) dialogue avec un modèle d'IA (Groq), peut joindre un PDF à son message pour des réponses fondées sur le document (RAG), et retrouve son historique persisté.

Fonctionnalités principales

  • Chat temps réel (typewriter), Markdown riche, coloration syntaxique + copie.
  • Envoi combiné PDF + message avec progression 0–100 %.
  • Modes Ask / Agent, sélecteur de modèle, palette Ctrl+K.
  • Thèmes sombre/clair, sidebar redimensionnable, suppression avec confirmation.

Chaîne d'appel : modèle demandé → GROQ_MODEL → fallbacks (dédupliqués, ordre gardé). Seule l'erreur model_not_found déclenche le suivant ; 401/429/timeout remontent aussitôt avec un message clair (502 + detail). Le modèle effectivement utilisé est retourné ({response, model}) et affiché dans le header. GET /api/models expose la allow-list (id + label) ; tout autre id → 400.

16. RAG approfondi (niveau entretien)

16.1 C'est quoi le RAG ?

Retrieval-Augmented Generation : au lieu de demander au LLM de répondre « de tête » (risque d'hallucination, ignorance de vos documents privés), on récupère d'abord les passages pertinents d'une base, puis on les injecte dans le prompt. Le modèle répond en s'appuyant sur du vrai contexte — vérifiable (citations [p. N]).

RAG (notre choix)Fine-tuningPrompt seul
Données privées/récentes✅ immédiat (upload → requêtable)❌ ré-entraînement coûteux❌ copier-coller manuel
CoûtFaible (index + requêtes)Élevé (GPU, dataset)Nul mais non scalable
Traçabilité✅ citations de pages❌ boîte noire✅ (texte fourni)
LimiteQualité du retrievalRigiditéTaille du contexte

16.2 Les 4 étapes dans Codenix (chiffres à connaître)

  1. Chunking : split 1000 caractères / overlap 200. Trop gros → bruit ; trop petit → contexte perdu. L'overlap évite de couper une phrase/figure en deux.
  2. Embeddings : all-MiniLM-L6-v2 → vecteurs de 384 dimensions, chargés paresseusement (démarrage rapide).
  3. Recherche vectorielle : FAISS (IndexFlatL2, distance euclidienne — plus petit = plus proche), k×3 candidats → filtre user → tri score → top_k=4. Index isolé par utilisateur + cache mémoire invalidé par mtime.
  4. Assemblage : blocs [source — p. N] + captions de figures + plafond 1800 car., injectés en message system avec règles de réponse.

16.3 Questions d'entretien RAG (avec réponses modèles)

QuestionBonne réponse (courte)
Pourquoi RAG plutôt que fine-tuning ?Données privées/évolutives sans ré-entraînement, coût faible, citations vérifiables. Fine-tune = style/comportement, pas connaissances.
C'est quoi un embedding ?Vecteur dense (ici 384 dims) où la proximité géométrique ≈ similarité sémantique ; deux phrases synonymes ont des vecteurs proches.
Cosinus vs L2 ?Cosinus = angle (insensible à la norme), L2 = distance euclidienne. FAISS FlatL2 ici ; avec vecteurs normalisés, les deux classent pareil.
Chunk size / overlap : trade-offs ?Gros chunks = plus de contexte mais bruit + tokens ; petits = précis mais fragmentés. Overlap 200 préserve les frontières. On tune par eval (fidélité des citations).
Top-k trop grand/petit ?Trop petit = réponse incomplète ; trop grand = bruit + coût tokens + dilution de l'attention (« lost in the middle »).
Comment gérez-vous les figures/UML ?Captions détectées (regex EN/FR) + compteur d'images par page en métadonnées ; le prompt ordonne de nommer et détailler chaque figure. Limite honnête : pas de vision — le modèle ne « voit » pas l'image.
Isolation multi-tenant ?Un index FAISS par user_id + filtre user_id à la requête : aucun chunk d'un autre user ne peut remonter.
Échecs typiques du RAG ?Mauvais chunking, k mal réglé, requête vague (→ reformulation), contexte contradictoire (→ instruction de priorité), figures purement visuelles.

17. LLM & Groq approfondis (niveau entretien)

17.1 Fondamentaux à maîtriser

  • Tokens : unités de texte (~4 caractères/token en anglais). Tout se facture/compte en tokens : prompt + raisonnement + réponse.
  • Fenêtre de contexte : 131k tokens ici — borne la taille historique + RAG injectable (d'où le cap 50 messages et 1800 car./bloc).
  • Modèles de raisonnement (GPT-OSS) : ils « réfléchissent » en tokens avant de répondre → d'où GROQ_MAX_TOKENS=4096 (1024 tronquait). Le fallback ne se déclenche que sur model_not_found, pas sur les 429.
  • Rôles : system (règles, non négociable), user, assistant. Notre system = règles maison + contexte RAG (+ instruction Agent).
  • Groq/LPU : puces d'inférence déterministes ultra-rapides (vs GPU généralistes) → latence sub-seconde, quotas stricts (429).
  • Hallucinations : mitigées par RAG + citations exigées + sanitize (jamais de bulle d'erreur renvoyée au modèle).
  • AsyncGroq partagé : 1000 chats concurrents multiplexés sur l'event loop au lieu de 40 threads (leçon du test de charge).

17.2 Questions d'entretien LLM (avec réponses modèles)

QuestionBonne réponse (courte)
Temperature / top-p, ça change quoi ?Contrôlent l'aléatoire : bas (≈0) = factuel/déterministe (idéal RAG), haut = créatif. Nous : défaut provider ; piste = baisser pour le factuel.
Pourquoi un modèle « décommissionné » a tout cassé ?ID en dur → 404 model_not_found → 500. Leçon : modèle configurable + fallback + 502 avec cause, jamais d'ID en dur.
Comment limitez-vous les coûts/latence ?Historique capé, blocs capés, top-k petit, quota via rate-limit (Redis prévu), infra-test sans IA, quota Groq monitoré (429).
Sync vs async pour les appels LLM ?Sync bloque un thread (~40 dispos) ; async multiplexe des milliers d'appels : indispensable sous charge.
Prompt injection — vous gérez ?Partiellement : sanitize (vide/placeholders), rôles validés, RAG prioritaire par instruction. Reste : garde-fous (Llama Guard prévu).
Évaluer la qualité des réponses ?Aujourd'hui : citations vérifiables + tests. Prévu : votes 👍👎, fidélité (faithfulness) vs sources, jeux d'éval.
